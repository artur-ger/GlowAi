## Слайд 4
Проблемы и гипотезы

Проблема (в зоне инженерии): 
Без стабильного end-to-end MVP нельзя проверить продуктовую гипотезу GlowAi: отпускник не получает план ухода под климат поездки за ≤5 минут.

Личная гипотеза (декомпозиция рабочей гипотезы проекта):
Если реализовать MVP-пайплайн FastAPI + Flutter/web (маршрут → климат home/destination → symptom-first + опц. селфи → план/packing-list) с p95 ответа analyze ≤30 с и сценариями «до поездки» / «SOS», то на пилоте ≥30 отпускников ≥80% завершат сценарий с time-to-plan ≤5 мин, а доля критических сбоев API/клиента составит <5%.

Критерии confirm/reject: time-to-plan; completion rate; error rate smoke; оценка «план применим» ≥4/5 (связка с порогом проекта ≥70%).

## Слайд 5
Анализ проблемы

Выводы из источников и исследований (основание гипотезы):

1. CustDev / питч GlowAi: боль travel-контекста — климат + недоступность понятного плана; альтернативы (поиск, ChatGPT, консультация) долгие/дорогие.

4. Инженерный вывод: ценность УЦП «за минуты» упирается в latency пайплайна, простоту входа (селфи опционально) и устойчивость API — это проверяемая тех.гипотеза.

## Слайд 6
Анализ проблемы (продолжение)

Технологический выбор под проверку гипотезы:

• FastAPI + Docker — быстрый контракт API и воспроизводимый стенд пилота.
• Климат: Open-Meteo (геокодинг + прогноз) без ключа на старте.
• Analyze: OpenAI-compatible vision-LLM с rule-based fallback (MVP без блокировки на обучение EfficientNet).
• Flutter / web UI — один клиентский контур для сценариев до поездки и SOS.
• Юр.минимум пилота: дисклеймер «не медуслуга», согласие на селфи, фото не хранится.

Связь с УЦП: скорость + персонализация под климат проверяются только если пайплайн реально укладывается в минуты на пилоте.

## Слайд 8
Методика проверки гипотезы

1. Зафиксировать 2 пользовательских сценария: A «до поездки», B «SOS на месте».
2. Прогнать технический smoke: /healthz, analyze (LLM и fallback), auth/checks (scripts/smoke-mvp.ps1, smoke-auth.ps1); flutter analyze без error.
3. Замерить latency analyze (цель p95 ≤30 с) на стенде пилота.
4. Рекрутинг ≥30 отпускников (общий пилот команды); для личной гипотезы учесть completion и time-to-plan по логам/наблюдению.
5. Собрать опрос после сценария: понятность плана (≥4/5), готовность следовать, баги UX/API.
6. Решение: confirm / доработать UX-поля и таймауты / pivot архитектуры (усилить rule-based, упростить вход без фото).
